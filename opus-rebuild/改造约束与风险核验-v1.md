## 三、已发现的既有缺陷

> 与本次改造**无直接关系**，顺手发现。严重度：**P0 影响识别正确性** / **P1 影响正确性但面窄，或影响可信度** / **P2 工程债** / **P3 文档与整洁**。

### D-1（P0）同义词扩展把 `_exact_keyword_bonus` 整个吃掉，影响 30% 语料

`match_rules` 先扩展再打分，而 `_exact_keyword_bonus` 判断的是「**整句**等于 keyword」：

```384:384:lch/matcher.py
    search = expand_query_with_synonyms(text)
```

```154:163:lch/matcher.py
def _exact_keyword_bonus(text: str, rule: Rule) -> float:
    text_l = text.strip().lower()
    text_ns = "".join(text.split()).lower()
    bonus = 0.0
    for kw in rule.keywords:
        kw_l = kw.lower()
        kw_ns = "".join(kw.split()).lower()
        if text_l == kw_l or text_ns == kw_ns:
            bonus += 8.0
```

一旦同义组命中，`search` 变成一长串，整句不再等于任何 keyword，**+8 分直接归零**：

```
触发同义扩展的语料行 = 70/232 (30.2%)
其中「本应拿 8 分 exact bonus 但被扩展吞掉」 = 66 行
  '刷新systemd' -> svc.daemon.reload (本应 +8)
  '查看异常服务' -> svc.list.failed (本应 +8)
  '卸载软件'     -> pkg.remove       (本应 +8)
  'apt安装'      -> pkg.install      (本应 +8)
全库口径：1534 个 keyword 里有 263 个（17%）自己当查询时 bonus 会被扩展归零
```

顺带第二个问题：扩展时**把命中的词自己也重复灌回去**，且整组词全部进入查询文本：

```
'内存占用' → '内存占用 内存占用 还剩多少内存 内存使用 看看内存 看内存 内存还剩'
  sys.mem.free   未扩展=14.50  扩展后=19.00  (exact bonus 8 → 0)
  sys.mem.model  未扩展= 2.70  扩展后= 5.20  ← 无关规则也白捡 2.5 分
```

即同义扩展**同时**做了三件坏事：吃掉精确加成、给自己重复计分、给同组其它规则免费加分。

### 4.1 关于第 6 条「74% / 22% / 4%」的详细复核

我把口径拆成四种一致组合，对同一批 232 行语料跑：

```
$ PYTHONPATH=. python3 /tmp/verify_match.py
=== 重叠口径敏感性（232 行语料） ===
  A 去空格·双向子串                     相等=77.6% 子串=22.0% 无重叠= 0.4%
  B 原样·双向子串                      相等=74.1% 子串=24.6% 无重叠= 1.3%
  C 去空格·仅 keyword⊆query          相等=77.6% 子串=22.0% 无重叠= 0.4%
  D 原样·仅 keyword⊆query           相等=74.1% 子串=24.6% 无重叠= 1.3%
```

对照上游的 `74% / 22% / 4%`：

- `74%` 只在**口径 B/D（不做空格归一化）** 下成立；
- `22%` 只在**口径 A/C（做空格归一化）** 下成立；
- `4% 无重叠` **在四种口径下都不成立**，实际最高只有 **1.3%（3 行）**，最低 0.4%（1 行）。

> **结论**：上游那三个数字**不是同一次测量的结果**，混用了两套归一化口径；而「仅 4% 无字面重叠」这个数**偏高 3~10 倍**。
>
> **方向上这不削弱上游的判断，反而加强它**：语料比上游说的**更自证**（按期望规则口径，77.6% 字面完全相等，仅 1.7% 无重叠）。但**具体数字不能引用**，方案里若复述 `74/22/4` 需改正。

无字面重叠的实际行（对全库任意 keyword，去空格口径）只有 1 行：`('用apt装', 'pkg.install')`。
按「仅对期望规则的 keyword」口径共 4 行：`查一下有没有 nginx 进程`、`找一下叫 application.yml 的文件`、`用apt装`、`看 nginx 错误日志`。

## 五、我认为最容易被方案忽略的 5 个点

### ① 测试套件对打分重写是**盲**的 —— 绿灯不代表没坏

86 个测试里只有 1 个会因量纲变化失败。**改完打分跑测试全绿，这个信号的信息量接近零。** 更糟的是，`_rank` 的 `or has_full` 逃生门（`matcher.py:350`）让阈值形同虚设，所以连「阈值语义变了」这种大改动，现有测试也完全察觉不到 —— 实测把 `t_exact`/`t_weak` 设成 `1e6`，语料 @1 仍有 90.9%、空结果只有 3 条。

**必须先把 ★T-10 / ★T-11 / ★T-12 写出来并冻结，再动 matcher。** 顺序反了就等于裸奔。

### ② margin 要在一个**本来就不按分数排序**的列表上算

判决层要用 `top1/top2 margin`。但 `_rank` 的首排序键是 `has_full` 布尔量（`matcher.py:339`），分数只是第二键，实测展示序分数非单调：`[24.54, 21.73, 24.6, 15.79, 10.24]`。

如果新代码沿用 `_rank` 的排序结果再取 `hits[0]`/`hits[1]` 算差值，**算出来的 margin 与"分数最高的两条之差"根本不是一回事**。上游报告本身就踩了这个坑 —— 它说「`重启nginx` top1 是 `nginx.config.view`(24.5)」，但真正的最高分是 `nginx.config.test` 的 **24.60**，只是被 `has_full` 压到了第 3 位。

### ③ 兜底的真正对手不是"阈值太高"，是 `rule.weight * 0.1` 这个常数先验

直觉上「返回空 → 把阈值降下来」就能出兜底候选。实测不是这样：当查询与所有规则零重叠时，每条规则的分数就等于它自己的 `weight * 0.1`（区间 `[0.70, 1.40]`），排序退化成 **weight 排序**，于是 4 条权重 14 的 `mirror.*` 规则霸占所有无意义查询的候选位：

```
'让它重新跑一遍'   → [mirror.maven 1.4, mirror.npm 1.4, mirror.overview 1.4, mirror.pip 1.4, im.notwork 1.4]
'这个软件不想要了' → 同上
'给这台机器加个新账号' → 同上
```

兜底必须建立在**真实相关性信号**（BM25 > 0 / object 槽位命中）上，并且要在归一化前把 `weight*0.1` 这个常数底分剥离。否则「不返回空」会变成「稳定返回四条镜像源规则」，体验比返回空更差。

### ④ 同义词扩展现在是**净负资产**，重建时必须一起处理，不能当成"已有能力"直接接上

`expand_query_with_synonyms` 同时干了三件坏事：
1. 让 30.2% 的语料行（66 行）失去本该拿到的 +8 精确加成（因为扩展后整句不再等于 keyword）；
2. 把命中的词**自己也重复灌回**查询（`'内存占用'` → `'内存占用 内存占用 还剩多少内存 …'`），等于给自己重复计分；
3. 把整组同义词灌进查询文本，**给同组其它规则免费加分**（`sys.mem.model` 白捡 2.5 分）。

方案的目标架构第二步就是「规范化/同义扩展」。如果直接复用这个函数，等于把上述三个缺陷原样带进新管线，而且在归一化打分下它们的破坏性更难察觉（分数被压到 0–1，肉眼看不出 19.00 vs 14.50 这种异常）。**同义词应当作用在"召回层的查询扩展"上（只影响召回集），不应该拼进用于打分的文本。**

### ⑤ 「低置信兜底」把安全边界从"不返回"挪到了"用户手一抖"，而审计里没有任何痕迹

三件事叠在一起：

1. 兜底会推出 `high` 风险意图。实测 `'把它转给另一个账号名下'` 的兜底 top1 是 `user.add`（`risk=high`，score 3.47）。
2. 否定检测有明显漏洞。`'别把服务停了'`、`'别停服务'`、`'千万别删了它'`、`'不想重启'` 全部 `detect_negation = False`。今天这些查询**返回空**，所以漏检无害；改成兜底之后，它们会**不带任何否定警示**地推出 stop/delete 类候选。
3. **审计不记录 `score` / `confidence`**（`audit.py` 的 record 字段里没有）。所以一旦线上出事，无法区分「用户确认执行的这条命令」当初是 exact 命中还是低置信兜底。

现有的风险闸只有 `confirm.py` 的 `risk_level` 分级，而规则库里 **critical 规则数为 0**，`high` 只有 17 条 —— 也就是说 `confirm.py:29-31` 那道最强的 critical 闸门，对规则路径**完全是死代码**。整个安全余量比看上去薄。

**最小补救（应写进方案，且成本极低）**：兜底候选排除 `high`/`critical`；`audit.py` 的 record 补 `score` / `confidence` / `negated` 三个字段；`negation.json` 的 `verbs` 补「停」「删」等单字与「停了」「删了」等口语形。
