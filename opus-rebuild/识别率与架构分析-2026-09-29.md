# 识别率与架构分析

日期：2026-09-29  
范围：`lch/matcher.py`、`lch/engine.py`、`lch/jieba_fallback.py`、`lch/preprocess.py`、`scripts/bench_corpus.py`、`tests/test_corpus.py`、`resources/rules.d/`、`resources/dict/`  
方法：静态阅读 + 只读脚本实测（本机当时无 jieba，走关键词兜底路径）。未改代码。  
方案正文：[匹配重建方案.md](./匹配重建方案.md)

结论：**问题不在规则条数不够，而在于 `.docs/命中率对照-重构后.md` 的 89.7% 测的不是识别能力；真实口语泛化约 @1=31%。根因是单层「关键词长度求和」既当召回又当排序。**

## 2. 基准不可信：89.7% 是自证

`scripts/bench_corpus.py` 用语料表当查询。这些查询词与规则 `keywords` 高度重合：

| 语料查询与 keyword 的关系 | 条数 | 占比 |
|---------------------------|------|------|
| 查询词 **完全等于** 某个 keyword | 172 | 74% |
| 查询词与 keyword **互为子串** | 50 | 22% |
| 与 keyword **无字面重叠**（真泛化） | 10 | **4%** |

96% 的样本在考「字符串能不能查到自己」。`matcher.py` 的 `_exact_keyword_bonus`：查询整句等于 keyword 时直接 +8，正好把这 74% 顶过 `t_exact=8`。基准再高也不会下降，和用户感受脱钩。

## 4. 架构问题

### 4.1 召回与排序未分离；打分是未归一化求和

`_score_from_hits` 把命中关键词权重累加；默认权重是字符长度 `float(max(len(kw), 1))`。关键词写得越多越长，全局得分越高，与匹配质量无关。

实测 `重启nginx`（这是 `nginx.restart` 的**字面** keyword）：

| 规则 | 得分 | 排名 |
|------|------|------|
| `nginx.config.view`（查看配置） | 24.5 | **第 1** |
| `nginx.config.test`（校验） | 24.6 | 第 3 |
| `nginx.restart`（正确答案） | 21.7 | 第 2 |

`nginx.config.view` 赢是因为 6 个关键词都含 `nginx`，6 次命中全部累加。这不是调参能救的，是计分模型的量纲问题。

关键词最多的规则当时：`im.notwork` 24 个、`perm.chown` 22 个、`env.path.write` 18 个；最少仅 3～4 个。堆词即堆分。

### 4.2 动词和名词同权

运维口语是「动作 + 对象」。对象名（nginx/docker/mysql）到处重复，**真正区分意图的是动词**，且动词决定风险。当前 schema 没有 `action` 字段，`重启` 和 `nginx` 都只是 keywords 数组里的字符串。`keyword_weights` 在 nginx 规则上当时全是 None。

实测 `停止nginx`：

| 规则 | 得分 | 结果 |
|------|------|------|
| `nginx.config.view` | 24.54 | **返回第 1** |
| `nginx.restart` | 10.23 | 返回 |
| `svc.restart` | 1.00 | 被阈值砍掉 |
| `svc.stop`（语义最接近） | **0.90** | 被阈值砍掉 |

用户说「停止 nginx」，第一条给「查看 nginx 配置」。`mirror.docker` 被 `docker.pull` 压制、`svc.status` 被 `nginx.*` 压制，同一病。

`不要重启nginx`：`nginx.config.view` 仍 24.5 排第一；`nginx.restart` 虽乘 0.25 降到 3.4，但查看配置不受否定影响（因 intent 不含 restart 等动词）。否定只打压「变更类 intent」，压不住「对象名堆词」的查看类规则。

### 4.3 阈值是绝对分数，与关键词写法耦合

`t_exact=8` / `t_weak=4` 是硬阈值，分数量纲是「关键词字符长度之和」：

- 短查询天然分低，整句返回空。
- 给某条规则补几个长关键词，**全局阈值语义就变了**。
- `LCH_T_EXACT` / `LCH_T_WEAK` 无法独立调——跟着规则文件漂移。

正确做法：归一化分数 + top1/top2 的 margin。

### 4.4 jieba 声明为主路径但可选，两条路径打分尺度不同

README 写 jieba 是「主路径分词匹配」，但是可选依赖。当时本机 `ModuleNotFoundError: No module named 'jieba'`。未安装时 `tokenize()` 返回空列表，走 `_naive_tokens` 的 2-gram 兜底。

`_score_rule_jieba_detail` 有额外 token 加分（`_keyword_weight(kw) * 0.35`），无 jieba 时不执行。**装不装 jieba 会得到不同排序**，阈值只有一套。文档基准也无法判断是在哪条路径下产生的。

停用词包含「看看」「查看」「哪个」等，口语里的有效词可能被切掉，进一步压低分。

### 4.5 无反馈回路；低置信兜底是返回空

- `history.json` 只写不读。用户在多命中里选了第 3 条这个信号永不进入排序。
- 213 条规则、1534 关键词、55 组同义词全靠手写枚举，维护成本 O(规则×说法)，规则文件之间无冲突检测（`nginx.*` vs `svc.*` 已实证打架）。
- 低置信时返回空，而不是降级到大类猜测。这是 21/45 空结果变成「不好用」的最后一环。

预处理只做 NFKC、全角数字/部分标点、空白压缩，不做口语归一（「干掉」≠「杀掉」，「挂了没」≠「状态」）。同义词扩展依赖查询里已能 `_hit` 到组内某词，改写过大则整组进不来。

## 5. 原型：只换打分、不动规则

同一份规则（keywords + desc 拼成文档），换成 **字符 2–3gram + IDF 余弦**，同一留出集：

| 指标 | 现状（求和 + 绝对阈值） | 原型（IDF 余弦） |
|------|-------------------------|------------------|
| accuracy@1 | 31.1% | **42.2%** |
| accuracy@3 | 44.4% | **55.6%** |
| accuracy@10 | 48.9% | **82.2%** |

IDF 降低「nginx」这类跨规则高频词的权重，不再让 `nginx.config.view` 靠堆词取胜。召回层重做是当时性价比最高、且不需要碰 213 条规则的一步。

实施方案见 [匹配重建方案.md](./匹配重建方案.md)。
