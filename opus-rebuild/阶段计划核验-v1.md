## 一、阻断级问题（Blocker）

### B-1　S4 的核心指标门槛在物理上不可达：瓶颈不在召回层

**问题**
计划 S4 的门槛表写明「全部为硬门槛，任一不达标则 S4 不通过」，其中最后一行是「held-out dev @10 | **显著上升**（见第五节路线图）| ★T-8」，路线图给的期望是 `held-out @10 〔估计 70–85%〕`、`held-out 空结果 〔估计 降到 5–15%〕`。

我按 S4 的规格（`keywords+desc` 的 2+3gram 字符倒排、BM25 `k1=1.2/b=0.75`、top-30、同义词生成召回变体列表取逐规则最大值、**打分用原始 query 跑 v1 的 `_score_rule_keywords_detail`、判决仍走 v1 `_rank`**）完整实现并实测：

```
=== ② held-out 口语集 (n=49) ===
  v1 现状（基线）                            @1=  8.2%  @10= 14.3%  空=35 (71.4%)
  S4 只换召回 top-30 (打分用原始query)          @1=  8.2%  @10= 14.3%  空=35 (71.4%)  recall@30= 73.5%
  S4 变体：打分用同义扩展串                       @1=  8.2%  @10= 14.3%  空=35 (71.4%)
  S4 变体：保留 v1 的 s>w*0.1 闸                @1=  8.2%  @10= 14.3%  空=35 (71.4%)
  S4 变体：纯 2-gram 索引                      @1=  8.2%  @10= 14.3%  空=35 (71.4%)  recall@30= 73.5%
  S4 变体：索引不含 desc                        @1=  8.2%  @10= 14.3%  空=35 (71.4%)  recall@30= 71.4%
```

**三个自变量（是否含 desc、2gram 还是 2+3gram、是否保留 `s>w*0.1` 闸）全部无差异**，端到端数字一个像素都没动。

**证据（归因实验，这是本轮最有价值的一次测量）**

```
=== 归因：held-out 上到底是谁在卡（n=49）===
  v1 现状                                       @1=  8.2%  @10= 14.3%  空=35 (71.4%)
  S4 召回top30 + v1打分 + v1判决(8/4)             @1=  8.2%  @10= 14.3%  空=35 (71.4%)
  S4 召回top30 + v1打分 + 判决放宽(2/1)            @1= 20.4%  @10= 59.2%  空= 4 ( 8.2%)
  S4 召回top30 + v1打分 + 判决全关(0/0)            @1= 20.4%  @10= 67.3%  空= 0 ( 0.0%)
  S4 召回top30 + 直接按 BM25 排序（无判决）          @1= 34.7%  @10= 67.3%  空= 0 ( 0.0%)

=== top_n 敏感性（held-out）===
  S4 top-10    @10= 16.3%   recall@10 = 67.3%
  S4 top-30    @10= 14.3%   recall@30 = 73.5%
  S4 top-50    @10= 14.3%   recall@50 = 73.5%
  S4 top-100   @10= 14.3%   recall@100= 73.5%
  S4 top-213   @10= 14.3%   recall@213= 73.5%     ← top-213 = 完全不做召回过滤
```

`top_n` 从 10 一路开到 213（等价于"不做召回"）端到端纹丝不动，这是「召回不是瓶颈」的直接证明。召回层把正确答案送进候选集的成功率是 **73.5%**，但端到端只有 **14.3%**，**59.2pp 的损失全部发生在 S4 原样保留的 v1 打分 + `t_weak=4` 判决上**：

```
=== S4 在 held-out 上被判决丢掉的条目里，期望规则的 v1 分数分布 ===
  召回命中但需过判决的 36 条，期望规则 v1 分数：
    min=0.70  中位=2.03  max=19.37   t_weak=4
    其中 s<4 且 has_full=False（必然被判决丢弃）= 28/36 = 77.8%
      s= 0.70  我现在是用哪个身份在操作       -> user.whoami
      s= 0.80  看看有没有定时跑的东西         -> cron.list
      s= 0.90  把容器关了                 -> docker.stop
      s= 1.00  不重启让网页服务器读新配置       -> nginx.reload
      s= 1.00  让它重新跑一遍               -> svc.restart
```

**为什么计划的类比不成立**
计划在第三节写：「原型实测同一留出集 @10 从 48.9% 升到 82.2%【实测】，S4 的估计区间即据此设定 —— 但原型是「换打分」，S4 是「换召回」，两者不完全等价，所以区间给宽」。

"区间给宽"这个补丁不够。原型的 +33pp 来自**换打分**，而换打分直接改变了「哪些候选能越过阈值」；S4 只改变「哪些规则被送去打分」，而打分函数对无字面重叠的规则本来就给出 0.7–2 分，判决线是 4 —— **候选集换得再准，也没有任何一条能多越过阈值**。这不是"不完全等价"，是**作用在完全不同的环节上**，两者的收益不可迁移。

**建议怎么改**

1. **把 S4 的门槛换成召回层自己的指标**，删掉端到端 held-out 门槛：
   - 主门槛：`recall@30 ≥ 95%`（对 in-corpus 232 条 + held-out dev）。当前实测 in-corpus recall@30 = 100%、held-out = 73.5%，**held-out 的 73.5% 本身就说明召回层还有 26.5% 的漏召回要治**，这才是 S4 真正该对付的问题，且计划完全没看到（它的"召回包含性"校验只针对 v1 能命中的 intent，而 v1 在 held-out 上只命中 14.3%，等于几乎不约束）。
   - 副门槛：`query()` p50 下降（实测 14.7ms → 2.1ms，轻松达标）、in-corpus @1 不劣化（实测 92.2% → 92.7%）。
2. **把路线图里 S4 行的 held-out 数字全部挪到 S6/S7 行**，并在正文明确写「召回层不产生端到端收益，它是 S6 打分层的前置基建」。
3. **决策 9(c) 的推荐要反转**。计划写「若必须压缩选 (c)，因为 S4 的召回层是收益最确定的一块」——实测恰恰相反，S4 单独上线收益为 0。最小可交付集合应该是 **S6a（换打分）+ S7（让阈值真正生效）**，S4 是它们的性能与候选质量前置，不是独立收益点。
4. 顺带修正 in-corpus 的估计：计划写 S4 末 in-corpus @1 〔估计 93–95%，D-1 修复带来的副产品〕，实测是 **92.7%（+0.5pp，1 行）**，不是 +1~3pp。

### B-2　S7 自己写的回滚路径（`LCH_MATCH_V2_VERDICT=0`）会因量纲错配而失效

**问题**
S7 的回滚一节写：「`LCH_MATCH_V2_VERDICT=0` 退回 v1 判决语义（含 `or has_full`），S6 的打分与排序保留。」

但 S6 已经把分数换成 0–1 余弦，而 v1 判决语义读的是 `LCH_T_EXACT`（默认 **8**）与 `LCH_T_WEAK`（默认 **4**）（`lch/matcher.py:377-378`）。0–1 的分数**恒小于 4**，于是 `s >= t_exact` 与 `s >= t_weak` 全部为假，唯一能放行的只剩 `or has_full`。而 S6 的 `_rank_v2` 已按 D-2 把 `has_full` 从排序键移除，计划没有说明 `has_full` 在 v2 里是否还被计算。

**证据**

```
--- 量化：现状下有多少查询存在 has_full=True 的规则（= VERDICT=0 时唯一的救命绳）---
  in-corpus  有 has_full 规则的查询 = 229/232 (98.7%)  -> 其余 3 条必然返回空
  held-out   有 has_full 规则的查询 =   8/49 (16.3%)  -> 其余 41 条必然返回空
```

- 若 v2 仍计算 `has_full`：in-corpus 看似正常（98.7% 有结果），**但全部被标成 `weak`**，`exact` 档彻底消失；held-out 则有 **83.7% 直接返回空**。
- 若 v2 不再计算 `has_full`：**100% 返回空**，回滚开关变成"关停开关"。

无论哪种，这都是**一个在生产现场用来救火的开关，按下去之后情况更糟且无声无息**。

反向的非单调组合同样危险：`LCH_MATCH_V2_RERANK=0`（退回 v1 打分）+ `LCH_MATCH_V2_VERDICT=1`（v2 判决，`LCH_V2_T_EXACT=0.35`）：

```
    v1 侧进入 _rank 的分数：min=2.30  p5=2.50  中位=8.98  max=93.16  (v2 T_EXACT=0.35)
    >>> 低于 0.35 的占比 = 0.0%  => 其余 100.0% 全部会被标成 exact
```

**100% 的候选被标成 `exact`** —— 在 S8 之后 `confidence` 会驱动 tips、`pick` 提示与 `agent` 二次确认（S8 新增的接线），这等于把所有兜底候选伪装成精确命中推给用户，直接击穿 C-9 的安全边界。

**建议怎么改**

1. **六个开关不是自由组合，要在代码里强制成一条单调降级阶梯**：
   `V2=0` ⊃ `FALLBACK=0` ⊃ `VERDICT=0` ⊃ `RERANK=0` ⊃ `SLOTS=0` ⊃ `RECALL=0`。
   在 `_match_rules_v2` 入口做一次规范化：**一旦某级关闭，其右侧（更外层）的级别一律强制关闭**，并向 stderr 打一行「已把 X 组合规范化为 Y」。这样 2^6=64 种组合塌缩成 **7 种合法配置**，测试矩阵从不可管理变成可穷举。
2. 规范化后，`VERDICT=0` 自动蕴含 `RERANK=0`，回滚就退到「S4 召回 + v1 打分 + v1 判决」，量纲自洽。
3. 把规范化后的**实际生效配置**（而不是用户传入的原始开关）写进 S3 新增的审计 `flags` 字段，否则灰度期仍然无法还原现场。
4. `_rank_v2` 里加一条硬断言：判决用的阈值与分数必须同量纲（例如 v2 分支断言 `0 <= score <= 1` 且阈值 < 1），不满足就 raise 而不是静默输出垃圾。

### B-3　S6 起步就欠 7.3pp / 1 条核心题，而计划把 D-2 当成"顺手修的显示缺陷"

**问题**
计划把 D-2（`_rank` 首排序键是 `has_full`、展示序非单调）定为 P0 但处置写的是「S6 `_rank_v2` 排序键去掉 `-int(has_full)`，改 `(-score, RISK_ORDER, intent_id)`」，并把 S6 的核心 20 条风险归因于「ngram 余弦对短查询区分度弱」，缓解手段是「优先调 `combine` 权重与 ×1.25 系数」。

实测表明，**在 v1 打分完全不变的前提下，单是把 `has_full` 从排序键拿掉，就已经破了 S6 的两条硬门槛**：

```
=== D-2 修复（排序键去掉 has_full）对核心 20 / 语料的实际影响 ===
    (v1 打分不变，只换排序键；这是计划 S6 `_rank_v2` 的排序键定义)

现状 v1 排序键 (-hasFull,-score,-weight,risk,id)  core20=20/20  @1= 92.2%  @10=100.0%  空=0  展示序非单调行=63
S6  排序键 (-score,risk,id) + 保留 or has_full    core20=19/20  @1= 84.9%  @10=100.0%  空=0  展示序非单调行=0
      掉: ('docker 有哪些容器', 'docker.ps', 'mirror.docker')
S6  排序键 (-score,risk,id) + 拆 or has_full(=S7) core20=19/20  @1= 84.9%  @10= 99.1%  空=0  展示序非单调行=0
      掉: ('docker 有哪些容器', 'docker.ps', 'mirror.docker')
```

含义：`has_full` 今天并不只是一个排序 bug，它实质上是一个**「整串 keyword 命中」的强先验**，独自扛着约 **7.3pp 的 in-corpus @1**。把它移除是正确的（否则 S7 的 margin 没有意义），但 v2 的余弦打分必须**先把这 7.3pp 挣回来，才谈得上净收益**。计划完全不知道这个坑，给的缓解只是一个标量系数（`×1.25`）。

顺带：`展示序非单调行 = 63/232`（27.2%）—— 核验文只举了 2 个例子，实际面广得多，★T-11 现状红得很彻底。这条对计划有利，说明 T-11 值得投入。

**建议怎么改**

1. 把「排序键改动」从 S6 里**单独拆成 S6-0**，在换打分公式之前先做，用 v1 打分单独测一次，把 −7.3pp / −1 条核心题**记录成 S6 的已知起点赤字**，而不是等 S6 结束时和余弦收益混在一起无法归因。
2. S6 的通过判据要相对「S6-0 之后的基线」而不是 S1 基线来读，否则会得到「余弦明明有效但门槛照样红」的误判。
3. `docker 有哪些容器 → mirror.docker` 这条掉题指向一个具体机制：`mirror.docker` 的 `weight` 更高且 `docker` 是它的 keyword。v2 里 `weight` 只做末位 tie-breaker（计划已写对），但这条题能否回来取决于余弦能否区分 `docker.ps`（keywords 含"有哪些容器"）与 `mirror.docker`。**建议把这一条列为 S6a 开工第一天的 smoke test**。
4. 顺带一处措辞矛盾：S6 改动范围写排序键是 `(-score, RISK_ORDER, intent_id)`（不含 weight），但同节设计决策写「`weight` 只作为排序的末位 tie-breaker（余弦完全相等时）」。两处对不上，实现时会各写各的。

### B-4　S5 的硬门槛「`object` 域数 = 32」在事实上就不成立（33 个域）

**问题**
计划 6 处写「32 个 object 域」，其中 **line 326 是 S5 的硬门槛**（"`object` 域数 = 32；schema 校验零失败"），line 636 是 held-out 覆盖要求（"32 个 object 域每域 ≥ 2 条"），line 663 是 dev/test 分层抽样依据。

**证据**

```
$ python3 -c "... Counter(r.intent_id.split('.')[0] for r in rules) ..."
规则数= 213
域数 = 33
只有1条规则的域 = 6 ['log', 'jdk', 'cron', 'sudo', 'swap', 'selinux']
只有2条规则的域 = 4 ['archive', 'firewall', 'mysql', 'redis']
```

计划（和上游核验文 C-12）沿用的 32 是错的，实际 33。**按字面执行，S5 的 schema 校验永远报 33 ≠ 32，S5 永远无法通过。**

**连带的逻辑矛盾**（这个比数字错更严重）：held-out 规范同时要求
- 「33 个 object 域每域 ≥ 2 条」，且
- 「**同一个 intent_id 的多条变体必须落在同一侧**」（dev/test 不跨半），且
- 「按 object 域分层抽样，保证域在两侧的条数尽量相等（差值 ≤ 1）」。

对 **6 个只有 1 条规则的域**，"每域 ≥ 2 条"意味着 2 条题都指向同一个 intent_id → 必须同侧 → 该域在另一侧覆盖为 **0**，与"两侧差值 ≤ 1"直接冲突（差值 = 2）。三条规则两两自洽不了。

**建议怎么改**

1. 把所有 `32` 改成 `33`，并且**不要把域数写成硬门槛**（规则库会增删，写死数字等于给未来埋雷）；改成「`object` 覆盖率 = 100% 且取值全部落在 `intent_id` 首段集合内」。
2. held-out 覆盖要求改成分层的：**规则数 ≥ 3 的域每域 ≥ 2 条且两侧各 ≥ 1 条**；**规则数 ≤ 2 的 10 个域每域 ≥ 1 条**，允许整域落在单侧，并在 `FREEZE.json` 里记录哪些域是单侧的。

### B-5　C-12 的槽位设计有两个会反噬的机制，计划的缓解不触及它们

**问题 ①：`action is null` 的重新归一化让未标动词的规则系统性占便宜（不是吃亏）**

计划写：「`action is null` 时把 0.45 按比例分摊给 object/modifier 后重新归一化，而不是给 0 分 —— 否则这批规则会被系统性压制」。方向是对的，但**分摊过头了**。

按计划的权重（action 0.45 / object 0.35 / modifier 0.20，`combine = 0.6*cos + 0.4*slot`）实算：

```
  action=null 的规则：权重重归一化 -> o:0.636  m:0.364

  场景 (o,m)                        标注规则     null规则    null 的相对优势
  o=1  m=1  动词命中=1               1.000      1.000      -0.000
  o=1  m=1  动词命中=0               0.550      1.000      +0.450
  o=1  m=0  动词命中=1               0.800      0.636      -0.164
  o=1  m=0  动词命中=0               0.350      0.636      +0.286
  o=1  m=0.5 动词命中=0              0.450      0.818      +0.368
```

关键是 **`动词命中=0` 这一行**。动词触发靠的是中文触发词集合的字面匹配，口语查询下经常打不中（"让它重新跑一遍"里没有"重启"）。此时**同一个 object 域内，一条标了 action 的正确规则只能拿 0.350，一条 `action: null` 的干扰规则却拿 0.636** —— 差 **+0.286 slot 分，折算到最终分是 +0.114**，而计划自己提的 `LCH_V2_MARGIN = 0.08` 只有 0.08。**一个纯归一化产物就能吃掉整个 margin 预算还有余。**

换句话说：动词标注得越认真，在动词没被识别出来时被惩罚得越狠；而 `null` 规则永远免检。这会让 S6b 的评估读数系统性偏向"槽位有害"，但真实原因是归一化方式，不是槽位本身没用。

**问题 ②：把 86 条"状态查询"统一标成 view/list 会让槽位在最需要区分的地方退化成常数**

计划对 84（实测 86）条不可推规则的处置是：「这类本质上是**状态查询**，绝大多数应标 `action: "view"` 或 `"list"`」。照做的后果：

```
  --- 若把「不可推断」全部按计划标成 view/list，各域内 (object,action) 的碰撞 ---
    域 mirror     规则=10  最大同 action 簇 = view×10  分布={'view': 10}
    域 net        规则=10  最大同 action 簇 = view×9   分布={'view': 9, 'info': 1}
    域 jvm        规则=10  最大同 action 簇 = view×9   分布={'view': 9, 'log': 1}
    域 sys        规则=18  最大同 action 簇 = view×13  分布={'view': 13, 'info': 2, 'list': 1, 'find': 1, 'kill': 1}
    域 java       规则=14  最大同 action 簇 = view×6   分布={'version': 2, 'view': 6, 'ps': 1, ...}
    域 echo       规则= 9  最大同 action 簇 = view×6   分布={'view': 6, 'list': 1, 'status': 1, 'write': 1}
  >>> 处在「同域同 action」簇里的规则总数 = 93/213 (43.7%)
```

对这 **93 条（43.7%）** 规则，一旦查询把 object 域定下来（这通常不难），`action` 与 `object` 两项（**占 slot 分的 0.80**）在簇内**完全相同**，槽位对区分度的贡献是 **0**。而 `combine = 0.6*cos + 0.4*slot` 意味着最终分里有一块恒定偏移，它**把余弦之间的差距压缩了 40%**，直接让 S7 的 margin 判决更难做。`mirror` 域 10/10 全是 view，是最极端的例子 —— 而 C-10 已经指出 `mirror.*` 正是退化路径的常客。

**建议怎么改**

1. **改归一化方式**：`action is null` 时不要把 0.45 分摊出去，而是给这一项一个**中性常数**（例如 `0.45 × p̄`，`p̄` 是标注规则在 dev 半上的平均动词命中率），让 null 规则既不被压制也不占便宜。或者更干脆：把 slot 从加权和改成**只对"命中的槽位"求和再除以"该规则可评的槽位数"**，让 null 规则的分母是 2 而不是 3，但分子也只有 2 项能拿分。
2. **`action` 枚举要能区分状态查询的子类**，不要都塞进 `view`。至少把 `view`（看单个对象的值）/ `list`（枚举多个）/ `status`（活着没）/ `info`（规格元信息）/ `usage`（用量）分开 —— 光这 5 类就能把 `sys` 域的 13 条 view 簇打散成 4–5 个簇。
3. **在 S5 交付时就产出这张碰撞表**（`slots_report.py` 应该报「同域同 action 簇的规模分布」），并设一条验收线：**最大簇 ≤ 域内规则数的 50%**。这比"人工抽检 30% 准确率 ≥ 95%"有用得多 —— 抽检只能发现标错，发现不了"标对了但没有区分度"。
4. 对 `mirror`（10/10 view）这种天然无动词差异的域，应当承认**槽位不适用**，靠 `object` + 余弦解决，而不是硬给 10 条规则贴同一个 view。

### W-2　`:.1f → :.4g` 在 v2 量纲下有三处可读性回退

计划 S3 的理由是「`.4g` 对 v1 量纲显示 `24.54`，对 v2 的 0–1 量纲显示 `0.8342`，一次改动同时服务新旧两套量纲」。这两个具体数字是对的，但只验了两个点：

```
  0.8312  .4g=0.8312      ✓
  0.75    .4g=0.75        ✓
  1.0     .4g=1           ← 满分显示成 "1"
  0.0     .4g=0           ← 零分显示成 "0"
  0.004821 .4g=0.004821   ← 宽度 8
  8e-05   .4g=8e-05       ← 科学计数法
  0.999949 .4g=0.9999
  列宽：v1 样本 .1f=[3,4,5] / .4g=[3,4,5]；v2 样本 .1f=[3] / .4g=[1,4,5,6,8]
```

1. **`1.0` 显示成 `[exact 1]`**。S6 定义「整句等于某 keyword 时 `cos = min(1.0, cos*1.25)`」，而核验文 C-5 实测 **77.6% 的语料查询字面完全等于某个 keyword** —— 也就是说 in-corpus 下**最常见的显示就是 `[exact 1]`**，看起来像坏了。

### W-6　held-out 主口径可用，但会把最大的几个域逼成不自然的表述

这是本轮 D 组的必做项，结论对计划**有利但需要加一段说明**。

被打掉的 8 条覆盖 docker（13 条规则，第二大域）、sys.cpu / sys.mem、java / jvm（14+10 条）—— **正是规则最密集、最该被测到的域**。要绕开就得说"把那个隔离环境里跑的东西停掉"这种没人会说的话，于是 held-out 在这些域上**不再代表真实用户语言**，测出来的分数是虚的。

1. 保留主口径做硬驳回，但**增加一条豁免**：允许查询包含"领域实体名词"（`docker/容器/java/内存/nginx/redis/mysql/k8s/…`，从 `intent_id` 首段与常见同义组派生，做成一张 20–30 词的白名单写进 `FREEZE.json`），只要**不包含期望规则的任何 keyword**即可。理由：用户不可能不说领域名词，禁掉它测的就不是识别能力而是造句能力。
2. 豁免词必须记进 `FREEZE.json` 的 `overlap_spec` 并在 bench 报告里**单独统计"含豁免词的题"的准确率**，与不含的分开看 —— 这样既保住可信度，又不至于把大域挖空。
3. 顺带：核验文 §4.2 给出的 `'把一堆文件打成一个包' 期望 archive.tar.create` 里 **`archive.tar.create` 这个 intent 在规则库中不存在**（实际是 `archive.tar.pack`）。这说明上一轮手写的 45 条里至少有 1 条期望值写错。S1 的 `overlap_check.py` **必须同时校验 `intent` 存在于规则库**，否则冻结的题库里会混进永远答不对的死题。

### W-7　「dev + test 方向一致」这个替代判据的假阳性率是 50%

计划自己算的置信区间是对的，我复核了：

```
   n=120 p=0.6  95%CI = ±8.8pp      （计划说"约 ±8pp" ✔）
   n= 60 p=0.6  95%CI = ±12.4pp     （计划说"约 ±12pp" ✔）
```

而且计划**主动打了补丁**：「路线图里凡是写 `±2pp` 的地方，判据应改用『dev + test 合并后方向一致』而非点估计」。加上路线图里所有 `±2pp` 都带 `〔估计〕` 标记，按计划自己的约定「〔估计〕不作为验收门槛」—— 所以**这一处不是自相矛盾，是已经打过补丁的**，应予肯定。

但补丁本身不够硬：真实效应为 0 时，两个独立半集的观测差符号各自 50%，**P(两半同向) = 0.5**。也就是说这个判据有 **50% 的假阳性率**，它不是显著性检验，只是"比看单点估计稍好"。用它来决定 S6b 是否保留（计划自评风险 1 承认这正是最可能的失败模式）是不够的。

**建议**：S6b 的去留改用**配对判据**而不是两半独立判据 —— 同一批 dev 题在 S6a / S6b 下逐条比对，统计「S6b 对而 S6a 错」与「S6a 对而 S6b 错」的条数，做 McNemar 检验（纯标准库可算）。配对设计能消掉题目难度方差，在 n=60 上的敏感度远高于比较两个独立比例。这是不加题量就能提升判别力的唯一办法。

### W-8　「test 半只允许跑 4 次」没有强制机制，而且预算是 0 余量

1. **无机制**。计划只在"度量纪律"里写了这句话，没有任何强制手段。`FREEZE.json` 的 sha256 校验管的是"题不许改"，管不了"结果不许反复看"。
2. **预算算不平**。计划列的 4 次是 S1 / S6 / S7 / S8，但 **S7 的验证方法里根本没有跑 test 半的命令**（只有 `--set heldout-dev` 的 S7-off / S7-on 对照）。所以实际排了 3 次，第 4 次悬空。
3. **零余量**。若 S6 的 gate 跑出来不达标，改完必须重跑，预算立刻超支，计划没有任何应对。

**建议**：把预算定成 **6 次（S1 / S6-gate / S6-regate / S7-gate / S8-gate / S8-regate）**并写明「每阶段最多 1 次重跑」；强制手段做成 `bench.py --set heldout-test` 时**必须**同时传 `--run-id <n>` 且向 `opus-rebuild/bench/test-runs.jsonl` 追加一条含代码 `git rev-parse HEAD` 与 `FREEZE.json` sha 的记录，`n` 与已有记录冲突则 `sys.exit(3)`。这挡不住蓄意绕过，但能挡住"顺手又跑了一次"，而后者才是过拟合的实际来源。

## 六、我认同方案哪些判断

挑错之外，下面这些是我实测后认为**方案做对了、不应该在返工中被改掉**的部分。

1. **S1/S2 严格前置，并加一次"反向元测试"。** 这是全计划最重要的正确决定。C-2 实测 86 个测试只有 1 个对量纲敏感，先建护栏再动刀是唯一负责任的顺序。而"monkeypatch 压成 0–1 后要求 T-10 仍绿、`test_matcher.py:76-77` 转红"这个元测试**核验文并没有要求**，是方案方自己补的，它检验的是护栏本身有效性，含金量很高。

2. **唯一侵入点选 `match_rules`、开关调用期读取。** 我核实了 `lch/engine.py:118-123` 确实是唯一调用点且不传阈值，选点判断完全正确；不选 `engine.query`（会把 `preprocess`/`extract_params`/`_to_hit` 卷进来）的理由也站得住。"照抄 `_env_float` 而不是 `ensure_jieba` 的 `_load_attempted`"这个细节抓得很准。

3. **S6 强制拆成 S6a / S6b。** 这是应对"槽位标注质量不可验证"的正确结构性手段，而且方案方在自评风险 1 里**诚实承认**这个缓解并不彻底（n=60 上 +3pp 无法区分于噪声）。这种自我怀疑的质量在方案文档里很少见。

4. **拆 `or has_full` 单独立项（C-3）。** 实测证明这个改动的代价比计划预期的还小（核心 20 条 0 依赖、@10 只掉 0.9pp、空结果率不变），但**把它单独隔离仍然是对的** —— 它是唯一直接改变"返回/不返回"集合的改动，事后归因的价值远大于合并上线省下的时间。

5. **同义词改成召回变体列表、打分用原始 query（D-1）。** 方向完全正确，实测 in-corpus @1 因此 92.2% → 92.7%，且"不拼长串、逐规则取变体 BM25 最大值"的做法同时消掉了 D-1 的三个子问题。

6. **兜底门槛用"余弦 > 0"而不是降阈值（C-10）。** 我复核了 `weight*0.1` 退化确实存在，方案选择在召回层根治而不是在兜底层补救，是对的；"不承诺空结果率 0%"这个克制也值得肯定 —— 它主动放弃了一个容易刷的指标。

7. **槽位写进 `rules.d/*.json` 而不是新建 `resources/slots.json`。** 实测完全正确：`Rule.raw` 全仓无消费者、`prepare_rules` 只把 keywords 喂给 jieba、现有字段集合无冲突，打包白名单与指纹脚本确实零改动。用户问的"改 rules.d 会不会反过来改变 `rules_sha256_16`" —— 会变（6a36…→b886…），但这是**正确行为**，且该指纹没有任何代码消费者（只有两处 README 文字），不会踩到别的东西。唯一要补的是发布说明里写清楚它变了两次。

### A. S4「只换召回」模拟的核心实现

```python
import math
from collections import Counter, defaultdict
from lch import matcher as M
from lch.loader import load_rules_bundle

rs = load_rules_bundle(ROOT / "resources" / "rules.json").rules
M.prepare_rules(rs, None); M._ensure_dicts()

def ngrams(s, ns=(2, 3)):
    s = "".join(s.split()).lower()
    out = []
    for n in ns:
        if len(s) < n:
            if s: out.append(s)
            continue
        out.extend(s[i:i+n] for i in range(len(s)-n+1))
    return out

def build_index(rs, ns=(2, 3), use_desc=True):        # keywords + desc 作为文档
    docs = [ngrams(" ".join(list(r.keywords) + ([r.desc] if use_desc else [])), ns) for r in rs]
    idx = type("I", (), {})()
    idx.n, idx.ns = len(rs), ns
    idx.doclen = [len(d) for d in docs]
    idx.avgdl = sum(idx.doclen) / max(len(docs), 1)
    post, df = defaultdict(list), Counter()
    for i, d in enumerate(docs):
        for t, c in Counter(d).items():
            post[t].append((i, c)); df[t] += 1
    idx.post = dict(post)
    idx.idf = {t: math.log(1 + (idx.n - v + 0.5) / (v + 0.5)) for t, v in df.items()}
    return idx

K1, B = 1.2, 0.75                                      # S4 规定不调参
def bm25(q, idx):
    sc = defaultdict(float)
    for t in set(ngrams(q, idx.ns)):
        for i, tf in idx.post.get(t, ()):
            dl = idx.doclen[i]
            sc[i] += idx.idf[t] * (tf*(K1+1)) / (tf + K1*(1 - B + B*dl/idx.avgdl))
    return sc

def variants(text, max_groups=4):                      # 同义词只生成召回变体，不拼长串
    out, tl, tns = [text], text.lower(), "".join(text.split()).lower()
    groups = [(g, [w for w in g if M._hit(tl, tns, w)]) for g in M._synonym_groups]
    for g, hit in [x for x in groups if x[1]][:max_groups]:
        src = max(hit, key=len)
        out += [text.replace(src, w) if src in text else text + " " + w for w in g if w != src]
    return out[:40]

def recall(text, idx, top_n=30):
    best = defaultdict(float)
    for v in variants(text):
        for i, s in bm25(v, idx).items():
            best[i] = max(best[i], s)
    cand = [(i, s) for i, s in best.items() if s > 0]
    cand.sort(key=lambda x: (-x[1], x[0]))
    return cand[:top_n]

def pipe_s4(text, idx, top_n=30):                      # 召回换掉，打分与判决完全沿用 v1
    negated = M.detect_negation(text)
    scored = []
    for i, _ in recall(text, idx, top_n):
        rule = rs[i]
        s, n_full = M._score_rule_keywords_detail(text, rule)   # 打分用原始 query（D-1 修复）
        rn = negated and M._intent_is_mutating(rule.intent_id, rule.keywords)
        if rn: s *= 0.25
        scored.append((s, rule, rn, n_full > 0))
    return M._rank(scored, 10, 8.0, 4.0)               # v1 的 _rank、v1 的 8/4 阈值
```

### B. held-out 主口径判定

```python
def norm(s):
    s = "".join(s.split()).lower()
    return "".join(" " if ord(c) == 0x3000 else
                   chr(ord(c)-0xFEE0) if 0xFF01 <= ord(c) <= 0xFF5E else c for c in s)

ALL_KW = [k for r in rs for k in r.keywords]                       # 全库 1534 个
SCOPE = [(k, norm(k)) for k in ALL_KW if len(norm(k)) >= 2]        # 排除 len 1（实际为空操作）

def reject(q):                                                      # 满足任一即驳回
    qn = norm(q)
    return any(n in qn for _, n in SCOPE) or any(qn in n for _, n in SCOPE)
```
