**阶段边界的三条铁律**（违反则该阶段无效）：

1. S1、S2 必须在 S4 之前全部完成并冻结。理由见 C-2 与核验文「最容易被忽略的第 ①」：现有 86 个测试对打分量纲近乎免疫，绿灯的信息量接近零。
2. S7 的「拆 `or has_full`」不得提前混进 S4/S6 的任何一次改动（C-3）。它是唯一一个会直接改变「命中/不命中」集合的改动，必须能被单独对照。
3. 每个阶段结束时，`LCH_MATCH_V2=0`（即不设）的行为必须与 S1 基线**逐条字节相同**。v1 路径永远是活的回滚目标。

### 分层开关设计（贯穿 S3~S8，回滚的唯一依托）

按 C-14 的建议 ①，唯一侵入点是 `lch/matcher.py` 的 `match_rules`（:368）函数体第一行。新增 `_env_flag(name, default=False)`，实现风格照抄同文件 `_env_float`（:358-365）——**调用期读取，不做模块级缓存**，否则测试无法在同进程内 A/B（C-14 末段、D-7）。

| 开关 | 关闭时的行为 | 引入阶段 |
|------|-------------|---------|
| `LCH_MATCH_V2` | 整条 v2 管线不进入，原样走 `match_rules` 旧实现 | S3 |
| `LCH_MATCH_V2_RECALL` | v2 内部退回「全量 213 条打分」，等价 v1 召回 | S4 |
| `LCH_MATCH_V2_SLOTS` | 重排忽略 `action`/`object` 字段（数据留着但不计分） | S5 |

| `LCH_MATCH_V2_VERDICT` | v2 内部退回 v1 的 `_rank` 判决（含 `or has_full`） | S7 |
| `LCH_MATCH_V2_FALLBACK` | 不产生兜底候选，低置信仍返回空 | S8 |

二级开关全部**默认开**（在 `LCH_MATCH_V2=1` 的前提下），这样生产回滚只需要关顶层开关；二级开关是给对照实验和精细定位用的。所有开关值必须进审计记录（S3 落地），否则线上出问题无法还原当时配置。

## S1　度量地基与 held-out 语料冻结

**目标**：拿到一套本轨道自己的、不写任何产品文档的度量工具，和一份改码前就锁死的 held-out 语料。

### 改动范围

| 路径 | 动作 |
|------|------|
| `opus-rebuild/tools/bench.py` | 新建。CLI：`--set {corpus,heldout-dev,heldout-test}`、`--out <dir>`、`--tag <阶段名>`。输出 `@1/@3/@10`、空结果率、每条 miss 明细、风险分布、p50/p95 延迟 |
| `opus-rebuild/tools/overlap_check.py` | 新建。held-out 字面重叠判定（口径见第六节），输出通过/驳回清单 |
| `opus-rebuild/tools/perf.py` | 新建。`Engine()` 构造与 `query()` 延迟的中位数/ p95（T-14 用） |
| `opus-rebuild/heldout/heldout-v1.jsonl` | 新建。冻结语料，每行 `{"q":..., "intent":..., "split":"dev"\|"test", "note":...}` |
| `opus-rebuild/heldout/FREEZE.json` | 新建。sha256 + 行数 + 口径参数 + 冻结日期 |
| `opus-rebuild/bench/S1-baseline.md` / `.json` | 新建。基线快照 |

**绝对不碰**：`scripts/bench_corpus.py`（它会覆写 `.docs/命中率对照-重构后.{json,md}`，C-15b）、`lch/`、`resources/`、`tests/`。

### 关键设计决策与取舍

- **bench 另起炉灶而非改 `bench_corpus.py`**。改它需要动输出路径，一旦漏改就污染产品文档；新写一个 120 行的脚本成本更低、副作用为零。代价是两套 bench 长期并存，需要在 `opus-rebuild/INDEX.md` 写明「本轨道只认 `opus-rebuild/tools/bench.py`」。
- **bench 启动即校验 `FREEZE.json` 的 sha256**，不匹配直接 `sys.exit(2)`。这是防「改代码时顺手改题」的唯一机械保障，比流程纪律可靠。
- **延迟测量与准确率测量放在同一个工具的两个子命令**，共用 Engine 构造逻辑，避免两处口径漂移。
- 脚本只依赖标准库（C-6），且必须能在 Python 3.8.10 下跑（首行 `from __future__ import annotations`）。

### 验证方法

```bash
cd /home/lilong/workspace/fat-dragon
# 语料基线（T-4 的基线来源）
PYTHONPATH=. python3 opus-rebuild/tools/bench.py --set corpus --out opus-rebuild/bench --tag S1
# held-out 判定（必须 0 条驳回才允许冻结）
PYTHONPATH=. python3 opus-rebuild/tools/overlap_check.py opus-rebuild/heldout/heldout-v1.jsonl
# 延迟基线（T-14 的基线来源）
PYTHONPATH=. python3 opus-rebuild/tools/perf.py
# 确认没碰产品文档
git status --porcelain .docs/ .review-ll/    # 必须为空输出（只看状态，不提交）
```

门槛：语料 bench 必须复现 **@1 = 92.2% (214/232)、@10 = 100%、空 = 0**（与核验文实测一致，不一致说明工具写错了）；`overlap_check` 驳回数 = 0；`perf.py` 报出 `Engine()` 与 `query()` 中位数并写入基线文件。

### 回滚

纯新增文件，删掉 `opus-rebuild/tools/` 与 `opus-rebuild/heldout/` 即可，对生产零影响。

### 风险与缓解

| 风险 | 缓解 |
|------|------|
| bench 与 `tests/test_corpus.py` 的语料解析口径不一致，导致两套数字打架 | `bench.py` 直接 `from tests.test_corpus import load_corpus_rows` 复用解析函数，不重写正则 |
| held-out 写题人不自觉地模仿 keyword 措辞 | `overlap_check.py` 硬判定 + 写题人与改码人隔离（见第七节需决策 1） |
| 一次性写 120 条质量不齐 | 分两批，第一批 40 条先跑判定校准手感，再写剩余 |

**工作量**：2 人日（工具 0.5，写题 1，判定返工与冻结 0.5）。

## S2　行为级护栏测试冻结

**目标**：把 6 类量纲无关的不变量测试写死在 `tests/` 里，其中现在就不成立的几条用 `expectedFailure` 标注并绑定解禁阶段。

### 改动范围

| 路径 | 动作 | 对应 |
|------|------|------|
| `tests/test_rank_invariants.py` | 新建。`rank(a) < rank(b)` 断言，不断言任何分数绝对值 | ★T-10 |
| `tests/test_display_order.py` | 新建。断言 `[h.score for h in hits]` 单调不增 | ★T-11（**现状红**） |
| `tests/test_threshold_effective.py` | 新建。`LCH_T_EXACT=LCH_T_WEAK=1e9` 时命中数必须为 0 | ★T-12（**现状红**） |
| `tests/test_fallback_risk.py` | 新建。兜底查询集的候选中不得出现 `risk_level ∈ {high, critical}` | ★T-13（**现状 vacuous**） |
| `tests/test_perf_budget.py` | 新建。`Engine()` ≤ 100ms、`query()` ≤ 17.9ms | ★T-14 |
| `tests/test_corpus.py:84-85` | 删除死代码 `marked` / `cls.core` 两行 | D-10 |
| `scripts/run_tests.sh` | 追加一次 `LCH_NO_JIEBA=1` 的独立进程运行 | ★T-16 |

### 关键设计决策与取舍

- **★T-10 的用例从哪来**：三个来源各取一部分——① 核验文 §4.2 列的 7 条崩溃样本（如 `'把容器关了'` 期望 `docker.stop` 排在 `docker.ps` 前）；② D-2 暴露的 `'重启nginx'` 应让 `nginx.restart` 排在 `nginx.config.view` 前；③ held-out dev 半里人工挑 20 组明确的「A 应在 B 前」。总量 ≥ 30 组。**只断言相对序，永不断言分数**，这是唯一能跨 v1/v2 量纲复用的资产。
- **现状就红的测试怎么办**：用 `@unittest.expectedFailure` 标注，并在 docstring 里写明 `解禁阶段: S6` / `S7` / `S8`。到了对应阶段，动作是**把装饰器删掉**并要求转绿——这比「到时候再写测试」强制力高一个量级，因为装饰器留在代码里，谁都看得见还欠着什么。`run_tests.sh` 仍报 OK，不阻塞 CI。
- **★T-14 的门槛写成「不劣于」而非固定毫秒数**：机器差异大。实现为读 `opus-rebuild/bench/S1-baseline.json` 里的基线值 × 1.15 作为上限；基线文件缺失时跳过（`skipTest`）而不是失败。
- **★T-16 起两个进程**：`LCH_NO_JIEBA` 被 `jieba_fallback.py:71-76` 的 `_load_attempted` 模块级缓存短路（D-7），同进程内切换是空操作。改 `run_tests.sh` 跑两遍是成本最低的正解；不去动 `_load_attempted` 的缓存逻辑（改动风险大于收益，见第四节 D-7）。

### 验证方法

```bash
bash scripts/run_tests.sh                     # 两个进程都必须 OK；用例数 86 → 约 100+
PYTHONPATH=. python3 -m unittest tests.test_rank_invariants -v   # 全绿（非 expectedFailure）
PYTHONPATH=. python3 -m unittest tests.test_display_order -v     # expected failure，不报 error
```

**S2 的验收里必须包含一次「反向验证」**：临时 monkeypatch 把 `_score_from_hits` 压成 0–1（复刻核验文 C-2 的实验），此时 `test_rank_invariants` 应当**仍然全绿**（证明它确实量纲无关），而 `tests/test_matcher.py:76-77` 的 `assertGreater(s, 4)` 应当红（证明实验生效）。这一步是检验护栏本身是否有效的元测试，不通过则 S2 不算完成。

### 回滚

删除新增测试文件、还原 `run_tests.sh`。不影响生产代码。

### 风险与缓解

| 风险 | 缓解 |
|------|------|
| ★T-10 的 30 组顺序断言里混入主观判断，后续成为改进的阻碍 | 每组必须写一句 `why`，且必须是「同一 object 域内动词明显不同」这类无争议对；有争议的进 held-out 而不进不变量测试 |
| `expectedFailure` 被长期遗忘 | 在 `opus-rebuild/INDEX.md` 挂一张「欠账表」，每阶段收尾时核对 |
| ★T-13 现在是 vacuous pass（兜底集今天返回空） | 用例里显式断言「候选数 > 0」作为前置，S8 前它是 expectedFailure，S8 后才有意义 |

**工作量**：1.5 人日。

## S3　零行为变更基建：V2 开关 + 审计 + 显示 + schema 告警

**目标**：把所有「不改任何匹配结果、但后续阶段都要用到」的基础设施一次铺完。

### 改动范围

| 文件:位置 | 改动 | 对应 |
|-----------|------|------|
| `lch/matcher.py` 新增 `_env_flag()`（紧邻 `_env_float`:358） | 调用期读环境变量，`{"1","true","yes","on"}` 为真 | C-14 |
| `lch/matcher.py:368` `match_rules` 函数体首行 | `if _env_flag("LCH_MATCH_V2"): return _match_rules_v2(text, rules, top_k, t_exact, t_weak, jieba_dict)` | C-14 ① |
| `lch/matcher.py` 新增 `_match_rules_v2()` | **本阶段内部逐行透传 v1**（复制 `match_rules` :383-408 的函数体），不改任何逻辑 | — |
| `lch/formatter.py:36` 与 `:57` | `:.1f` → `:.4g` | C-1 |
| `lch/audit.py:21-24` `append_audit` | record 增补 `score` / `confidence` / `negated` / `match_engine`（v1/v2）/ `flags`（开关快照） | C-13 |
| `lch/agent.py:95,113`、`lch/step_mode.py`、`lch/script_mode.py` 的 `append_audit` 调用点 | 从 `HitView` 透传上述字段 | C-13 |
| `lch/agent.py:131` `_apply_hit` 返回值 | 增加 `confidence`，供后续 S8 接线；本阶段只透传不使用 | C-1 |
| `lch/loader.py:84-89` `_parse_rule` | 加载期 `warnings.warn` / stderr 告警三类问题：`risk_level` 非法值被降级、`keyword_weights` key 不在 `keywords`、同规则内忽略大小写后重复的 keyword。**只告警，不改任何取值** | C-11 / D-3 / D-5 |

### 关键设计决策与取舍

- **`:.1f` → `:.4g` 而不是 `:.3f`**。`:.4g` 对 v1 量纲显示 `24.54`（与今天几乎一致），对 v2 的 0–1 量纲显示 `0.8342`（候选可区分）。一次改动同时服务新旧两套量纲，S8 翻默认时不需要再动 formatter。`:.3f` 会把今天的 `24.5` 变成 `24.540`，属于无谓的视觉回归。
- **`_match_rules_v2` 本阶段是纯复制粘贴**。这看起来浪费，但它让 S4~S7 的每一次改动都只包含该层的真实逻辑，且「开关有效性」这件事被单独验证过一次。如果直接在 S4 里同时引入开关和新召回，一旦出问题无法区分是开关接错了还是召回写错了。
- **loader 只告警不修正**（D-3/D-5）。修正 `_exact_keyword_bonus` 的大小写重复会让 `sys.cpu.model`、`env.path.write` 的分数腰斩（核验文 D-3 实测虚高 13~27 分），属于行为变更，会污染 S1 基线。v2 的文档化打分天然用 set 去重，这个缺陷在 S6 自动消失；v1 路径保持带病运行，作为对照锚点。
- **审计补的 `flags` 字段记开关快照**，格式 `"V2:1,RECALL:1,RERANK:0"`。灰度期间这是唯一能回答「这条命令当初走的哪条路径」的证据（C-13）。

### 验证方法

```bash

# 开关有效性：两条路径结果必须逐条相同
PYTHONPATH=. python3 opus-rebuild/tools/bench.py --set corpus --tag S3-v1
LCH_MATCH_V2=1 PYTHONPATH=. python3 opus-rebuild/tools/bench.py --set corpus --tag S3-v2
diff opus-rebuild/bench/S3-v1.json opus-rebuild/bench/S3-v2.json   # 必须无差异
# 同进程 A/B 能力（防 C-14 末段的缓存陷阱）
PYTHONPATH=. python3 -c "
import os; from lch.engine import Engine
e=Engine();
os.environ['LCH_MATCH_V2']='1'; a=[h.intent_id for h in e.query('查看内存').hits]
os.environ['LCH_MATCH_V2']='0'; b=[h.intent_id for h in e.query('查看内存').hits]
assert a==b; print('同进程切换 OK')"
# 显示格式
PYTHONPATH=. python3 -m lch "重启nginx" | head -8
# 审计字段
LCH_AGENT_AUDIT=1 ... && tail -1 ~/.lch/data/agent_audit.jsonl | python3 -m json.tool
```

门槛：T-1 全绿；**S3-v1 与 S3-v2 的 bench 输出必须字节相同**；与 S1 基线也必须字节相同；审计 JSONL 里能看到 `score`/`confidence`/`negated`/`flags` 四个新键；loader 告警条数 = 1 条 `keyword_weights` 丢弃 + 2 条规则的大小写重复（与核验文实测数一致，对不上说明告警逻辑有误）。

### 回滚

不设 `LCH_MATCH_V2` 即回到原路径（v2 此刻也等价，所以无风险）。formatter 与 audit 的改动是显示/记录层，需要回滚时改回两行常量即可，不依赖 git。

### 风险与缓解

| 风险 | 缓解 |
|------|------|
| `append_audit` 调用点分散在 4 个模块 13 处，漏改导致字段不齐 | 改成在 `append_audit` 内部从一个可选的 `hit` 参数统一提取，调用点只多传一个参数；漏传时字段为 `null` 而不是缺失 |

**工作量**：1 人日。

## S4　召回层：ngram 倒排 + BM25 取 top-30

**目标**：把「哪些规则进入打分」从「全量 213 条 + `s > weight*0.1` 闸」换成「倒排召回 top-30」，同时把同义词从打分文本里摘出来。

### 改动范围

| 路径 | 内容 |
|------|------|
| `lch/retrieval.py`（新建） | `build_index(rules) -> Index`：对每条规则把 `keywords + desc` 拼成文档，切 2-gram 与 3-gram，建 `term -> [(rule_idx, tf)]` 倒排 + `df` + `idf`。`recall(query, index, top_n=30) -> list[tuple[int, float]]`：BM25（`k1=1.2, b=0.75`，参数放模块常量便于 S6 调）。纯 `math` + `collections`，无第三方依赖（C-6） |
| `lch/retrieval.py` | `expand_for_recall(text) -> list[str]`：返回「原查询 + 每个命中同义组的替换变体」的**列表**，不拼成一个长串。召回时对每个变体各跑一次 BM25 取 max（D-1） |

### 关键设计决策与取舍

- **本阶段不换打分公式，只换召回集合**。这是让 S4 可独立归因的核心：唯一的变量是「进入打分的规则从 213 条变成 30 条」。分数量纲不变，`_rank` 不变，formatter 不变，所以 S1 基线里 in-corpus 的所有数字都还能直接比。
- **同义词只影响召回集，不进入打分文本**（D-1）。做法是生成变体列表而非拼接长串，召回时取各变体 BM25 的逐规则最大值。这一步同时消灭 D-1 的三个问题：`_exact_keyword_bonus` 的 +8 回来了（30.2% 语料行受益）、命中词不再重复灌回、同组其它规则不再白捡分。**预期 in-corpus @1 会因此上升**，这是 S4 的一个副产品收益。
- **`weight * 0.1` 常数先验在召回层就排除**（C-10）。BM25 分数为 0 的规则一律不进 top-30，哪怕它 weight=14。这样「无意义查询稳定返回 4 条 mirror.*」的退化路径从根上被切断，而不是靠 S8 的兜底去补救。召回不足 30 条时就返回不足 30 条，**不补齐**。
- **不落盘**（C-7）。实测建 2+3gram 倒排 +14.9ms，而现状单次 `query()` 就要 17.9ms（C-8）。落盘会同时踩「不进 tar」「不进指纹」「索引与 rules 版本不一致」三个坑，收益却只有十几毫秒，明显不划算。
- **3-gram 要不要上**：默认 2+3gram（+14.9ms）。若 T-14 在 arm64 上不达标，降级为纯 2-gram（+6.6ms），代价是召回率下降，需要在 S4 内用 dev 半做一次 A/B 再定。

- **84 条不可推动词的处理（C-12）**：分三类处理，不允许「全靠自动推断」。

- **回滚不靠删数据，靠关开关**：`LCH_MATCH_V2_SLOTS=0` 时重排完全忽略这两个字段。所以标注数据可以先合入、后生效，也允许标注质量不佳时立即停用而不必回退 26 个 JSON 文件。

## S6　重排层：IDF 余弦 + 槽位加权 + 0–1 归一化

**目标**：把 v2 的打分从 v1 的「关键词长度求和」换成「keywords+desc 文档的 2–3gram IDF 余弦 + action×object×modifier 槽位加权」，输出 0–1 分并**严格按分数排序**。

> **本阶段强制拆成两个可独立回滚的子步**，这是应对「槽位标注质量不可验证」的唯一手段：
> - **S6a**：只换打分公式（IDF 余弦），`LCH_MATCH_V2_SLOTS=0`。这一步复现核验过的原型收益。
> - **S6b**：在 S6a 之上叠加槽位加权，`LCH_MATCH_V2_SLOTS=1`。单独测量槽位的边际收益。
> 如果 S6b 的 held-out dev 指标不优于 S6a，就**停在 S6a**，把 S5 的标注数据留着不生效（见第八节自评风险 1）。

### 改动范围

| 路径 | 内容 |
|------|------|
| `lch/rerank.py`（新建） | `score_v2(query, rule, index) -> float`：查询与规则文档的 2–3gram IDF 加权余弦，值域天然 [0,1]。文档 ngram 集合**用 set 去重**（D-3 在此天然消失） |
| `lch/rerank.py` | `slot_score(query, rule) -> float`：`action` 命中（权重建议 0.45）× `object` 命中（0.35）× `modifier`（0.20）。`action is None` 时把 0.45 按比例分摊给 object/modifier 后重新归一化 |
| `lch/rerank.py` | `combine(cos, slot) -> float`：建议 `0.6*cos + 0.4*slot`，两项均已在 [0,1]。权重放模块常量 |
| `lch/matcher.py` `_match_rules_v2` | `_env_flag("LCH_MATCH_V2_RERANK", True)` 时用 `rerank.score_v2` 替换 v1 的 `_score_rule_*_detail` |
| `lch/matcher.py` 新增 `_rank_v2()` | 排序键改为 `(-score, RISK_ORDER, intent_id)`。**`has_full` 不再作为排序键**（D-2）。判决仍沿用 v1 的 `t_exact/t_weak` 语义（含 `or has_full`），等 S7 再动 |
| `lch/matcher.py` `_match_rules_v2` | 否定降权 `s *= 0.25` 沿用（在 0–1 量纲下同样有效） |
| `tests/test_display_order.py` | **摘掉 `@unittest.expectedFailure`**，必须转绿（★T-11） |

### 关键设计决策与取舍

- **0–1 归一化的具体定义**：余弦本身就在 [0,1]，不需要额外的 min-max（min-max 会让「所有候选都很差」的情况下 top1 也拿到 1.0，这正是兜底层最怕的）。绝对余弦值可以横向比较不同查询，这是 S7 的 margin 判决能成立的前提。
- **`weight` 怎么办**：v1 的 `rule.weight * 0.1` 常数底分（C-10）在 v2 里**彻底不用**。`weight` 只作为排序的末位 tie-breaker（余弦完全相等时），不进入分值。这样归一化前就不存在需要剥离的常数项。
- **`_exact_keyword_bonus` 的 +8 怎么迁移**：不迁移成加分，改为**乘性提升**——整句等于某 keyword 时 `cos = min(1.0, cos * 1.25)`。理由：0–1 量纲下加 8 会直接溢出；而且 D-3 的「粘两次同一个词分数翻倍」在乘性+set 去重下不可能复现。
- **分开 S6a/S6b 的代价**：多一次完整的 bench 与评审，约 0.5 人日。值得，因为「换公式」和「加槽位」是两个独立的赌注，混在一起失败时无法归因。
- **jieba 路径怎么办**：v2 的余弦基于字符 ngram，**不依赖分词**。jieba 可用时作为 modifier 槽位的辅助信号（提取动词），不可用时 modifier 退化为 ngram 匹配。这样 C-6 的「零强制依赖」和方案里 P2 的「两路径同一套打分公式」一次性达成，`match_rules(use_jieba=)` 这个死参数（D-7）在 v2 里不再引入。

### 风险与缓解

## S7　判决层：margin 判决 + 拆除 `or has_full` 逃生门

**目标**：让 `t_exact` / `t_weak` 真正生效，并用「归一化分 + top1/top2 margin」给出 exact / weak / 低置信三态。

> 这是全计划**唯一一个会直接改变「返回 / 不返回」集合**的阶段，按 C-3 单独立项、单独对照。

### 改动范围

| 路径 | 内容 |
|------|------|
| `lch/matcher.py` `_rank_v2` | `_env_flag("LCH_MATCH_V2_VERDICT", True)` 时启用新判决：`score >= T_EXACT and margin >= M_EXACT` → `exact`；`score >= T_WEAK` → `weak`；否则 → `low`（S8 前直接丢弃，与今天行为一致）。**删除 `or has_full` 分支** |
| `lch/matcher.py` `_rank_v2` | margin 定义：`hits[0].score - hits[1].score`，且**必须在按分数排好序的列表上取**（D-2 已在 S6 修复，此处加 assert 守卫）。只有 1 条候选时 `margin = hits[0].score` |

### 关键设计决策与取舍

- **阈值默认值怎么定**：不能拍脑袋。做法是在 S6 结束后，用 dev 半 + in-corpus 画一条「阈值 → (@1, 空结果率, 误召回率)」曲线，选「in-corpus 空结果率 = 0 且 dev 空结果率最低」的点。这条曲线本身作为 S7 的交付物存进 `opus-rebuild/bench/S7-threshold-sweep.md`。
- **拆 `or has_full` 的直接后果是空结果率上升**。今天这个逃生门让 `t_exact=t_weak=1e6` 时 in-corpus 仍有 90.9% @1（C-3 实测），拆掉后阈值第一次真正生效。**S7 单独交付但不单独发布**：它与 S8 打包成同一个灰度批次，因为在兜底层上线前，S7 会让部分查询从「有结果」变成「无结果」，是阶段性体验劣化。

### 关键设计决策与取舍

- **兜底的门槛是「余弦 > 0」而不是「降低阈值」**（C-10、核验文第 ③ 点）。降阈值会让常数先验主导，稳定吐出 4 条 mirror.*，体验比返回空更差。v2 已经不使用 `weight*0.1`，所以「无任何 ngram 重叠 → 余弦 0 → 不返回」是自然结果，**空结果不会被消灭到 0，而是被压到真正无信号的少数查询上**。这一点要在指标路线图里如实标注，不承诺 0%。
- **high 风险直接排除而非降位**（推荐）。理由：兜底本身就是低置信，把一条 `user.add` 放在第 3 位仍然只要用户手一抖就会进确认流程，而 `confirm.py:33` 的 YES 门槛对「以为系统猜对了」的用户没有实质保护力。排除的代价是少数合法的 high 意图在口语查询下拿不到兜底——可接受，因为用户可以换更明确的说法。**此项需用户确认**（决策 3）。
- **`fallback` 是第四个 confidence 取值**。C-1 指出 confidence 今天零行为消费，所以新增取值对现有代码零影响；但 `formatter` / `pick` / `agent` 三处接线是**全新增的**，必须一起交付，否则用户看到的兜底候选与 exact 候选长得一模一样。
- **打包一致性**：v2 不新增任何 `resources/` 文件（索引不落盘，槽位写进已有规则文件），所以 T-18 天然满足，`build_release.sh:97-113` 的白名单**不需要改**。只改 `:129-134` 的指纹覆盖面是为了顺手修 D-9（改 `synonyms.json` 指纹不变）——这一行改动会让 `rules_sha256_16` 的值变化一次，需要在发布说明里注明。
- **翻默认的方式**：把 `_env_flag("LCH_MATCH_V2")` 的 default 改成 `True`。运维现场回滚是 `export LCH_MATCH_V2=0`，**不需要重新打包、不需要重启服务之外的任何操作**。这是选 C-14 方案 ① 的最大回报。

## 三、指标路线图

**数据来源标注约定**：`【实测】` = 核验方已跑出的数字，可直接引用；`【待测】` = 该阶段必须实际跑出、当前无值；`〔估计〕` = 本计划的预期区间，**不作为验收门槛**，只用于判断「方向是否跑偏」。

### 基线（S1 结束时锁定）

| 指标 | in-corpus (n=232) | held-out (新冻结，n≈120) |
|------|-------------------|--------------------------|
| @1 | **92.2%【实测】** | 【待测】〔估计 30–40%〕 |
| @10 | **100%【实测】** | 【待测】〔估计 35–50%〕 |
| 空结果率 | **0%【实测】** | 【待测】〔估计 40–50%〕 |
| 核心 20 Top-1 | **20/20【实测】** | 不适用 |
| `query()` p50 | **17.9ms【实测】** | 同左 |

held-out 的三个估计区间来自核验方自写 45 条的实测（@1 35.6% / @10 37.8% / 空 44.4%）与方案方 45 条的实测（@1 31.1% / @10 48.9% / 空 21 条），**这两套都不是本计划要冻结的集合，所以只能当区间参考，不能当基线**。S1 必须重测。

S4 的 held-out @10 是全计划最大的单点跃迁，因为它同时解决了「`s > weight*0.1` 闸挡掉弱相关规则」与「同义扩展吃掉精确加成」两件事。原型实测同一留出集 @10 从 48.9% 升到 82.2%【实测】，S4 的估计区间即据此设定——但原型是「换打分」，S4 是「换召回」，两者不完全等价，所以区间给宽。

### 度量纪律

- test 半在整个计划中只允许跑 **4 次**：S1（基线）、S6（关口）、S7（关口）、S8（终验）。每次结果必须写进 `opus-rebuild/bench/` 并注明跑之前的代码状态。

## 四、held-out 语料构造规范

### 谁写、写多少

| 项 | 规定 |
|----|------|
| 写题人 | ≥ 2 人，且**不得是 S3–S8 的改码人**。若人力只有 1 人，则必须在 S1 完成冻结后才允许开始读 `matcher.py` 的打分逻辑 |
| 数量 | 目标 **120 条**（dev 60 / test 60）；最低 **90 条**（dev 45 / test 45），下限由 ★T-8 的「≥45 条」推出——注意 45 条是**单个 split** 的下限，不是总量下限 |
| 覆盖 | 32 个 object 域每域 ≥ 2 条；`risk_level = high` 的 17 条规则至少覆盖 5 条（兜底风险闸要有样本） |
| 每条字段 | `q`（口语查询）、`intent`（期望 intent_id）、`split`、`note`（为什么这么问，一句话） |

写题指导原则（写进 `opus-rebuild/heldout/README.md`）：**用「用户会怎么描述这个问题」而不是「这条规则叫什么」**。核验方的关键实验已经证明，把语料原句套上口语外壳（礼貌前缀、第一人称、填充词）对识别几乎无影响（@1 只从 92.2% 掉到 ~89%，@10 保持 100%）——**失效条件是无共享字面，不是口语化或句子长**。所以写题时要刻意换一套词汇去描述同一件事（「这台机子开了多久没关过了」而不是「查看运行时间」），而不是给原句加长度。

### 零字面重叠的判定口径

C-5 指出上游的 `74/22/4` 混用了两套归一化口径。本计划**固定一套口径并写死在脚本里**，任何地方引用重叠比例必须注明用的是哪套。

**主口径（判定用，硬性）**：

1. 归一化：`s -> "".join(s.split()).lower()`，再做全角→半角转换。（即核验文的口径 A/C 的「去空格」侧）
2. 比较范围：**全库 1534 个 keyword**（不只是期望规则的 keyword）。
3. 排除长度 1 的 keyword（否则单个汉字会让几乎任何句子被判重叠）。
4. 驳回条件（满足任一即驳回，需重写）：
   - 存在某个 `len ≥ 2` 的 keyword 是查询的子串；
   - 查询是某个 keyword 的子串。

**副口径（报告用，不驳回）**：

- 对**期望规则**的 keyword 单独跑一遍同样判定，结果记入报告（应当全部「无重叠」，若有例外必须逐条说明）。
- 与**期望规则 desc** 的最长公共子串长度，≥ 4 时标记为软告警。desc 也进入 v2 的打分文档（S6），desc 重叠会带来和 keyword 重叠同样的自证效应，但完全避免不现实，所以只记录不驳回。

**引用纪律**：本计划及后续所有 `opus-rebuild/` 文档，引用语料自证比例时一律用 **77.6% 完全相等 / 20.7% 互为子串 / 1.7% 无重叠**（按期望规则 keyword、去空格口径，核验文实测）。早期文档里流传的另一组三联数字**禁止引用**——它混用了两套归一化口径，且「无重叠」一项偏高 3~10 倍，出处与复核见核验文 §4.1。

### dev / test 切分

- **按期望 intent 的 object 域分层抽样**，保证 32 个域在两侧的条数尽量相等（差值 ≤ 1）。
- **同一个 intent_id 的多条变体必须落在同一侧**。否则 dev 上的调参会通过「这个 intent 的表述习惯」泄漏到 test。
- 切分由脚本 `opus-rebuild/tools/split_heldout.py` 用固定 `random.seed(20260929)` 完成，切分结果直接写进 jsonl 的 `split` 字段，不在运行时重切。

### 冻结机制

1. 写题 → `overlap_check.py` 判定 → 驳回项重写 → 循环到 0 驳回。
2. `split_heldout.py` 打 split 标签。
3. 生成 `FREEZE.json`：

```json
{
  "file": "heldout-v1.jsonl",
  "sha256": "<64 hex>",
  "n_total": 120, "n_dev": 60, "n_test": 60,
  "frozen_at": "2026-09-XX",
  "overlap_spec": {"normalize": "strip_space+lower+fullwidth2half",
                   "scope": "all_keywords", "min_kw_len": 2,
                   "reject_if": ["kw_in_query", "query_in_kw"]},
  "split_seed": 20260929
}
```

4. `bench.py` 每次启动重算 sha256，不匹配立即 `sys.exit(2)` 并打印差异行号。
5. 冻结后**只允许删、不允许改**。若发现某条题目本身标错了期望 intent，动作是把它移到 `heldout-rejected.jsonl` 并在 `FREEZE.json` 记一次 `revision`，**重算 sha256**，同时在所有后续 bench 报告里标注「n 从 120 降到 119」。绝不允许原地修改题面。
6. held-out 文件全部在 `opus-rebuild/heldout/` 下，**不在 `resources/`**，所以不进打包白名单、不进 `rules_sha256_16`，C-7 的两个坑与它无关。

## 六、自评风险：本计划最可能失败的三个地方

### 风险 1　S5 的 84 条人工动词标注是全计划唯一不可验证的环节，且它的失败会被 S6 掩盖

C-11 明确指出 `action` 写错会完全静默；S5 引入的枚举校验只能挡拼写错误（`"restrat"`），挡不住语义标错（把 `net.port.listen` 标成 `list` 而不是 `view`）。更糟的是，如果 S6 一次性同时换打分公式和加槽位，槽位的负收益会被余弦的正收益掩盖，最后得到一个「整体提升了，但其中一半的改动实际是在拖后腿」的结果，而且无法归因。

这也是本计划强制把 S6 拆成 S6a/S6b 的原因。但这个缓解并不彻底：S6b 的边际收益如果是 +3pp，在 n=60 的 dev 半上（95% CI ≈ ±12pp）根本无法区分于噪声。**真实的失败模式是：我们会在统计噪声里做一个二选一的决定，然后用它作为后续所有工作的地基。** 如果发生，最可能的表现是 S7 的阈值 sweep 怎么调都找不到一个同时满足 in-corpus 和 held-out 的点。

### 风险 2　held-out 集太小，而计划里有 7 个判据依赖它

n=120（dev/test 各 60）在统计上支撑不了本计划要求的判定精度。S4 的 +30pp 跃迁能测出来，但 S6b 的边际收益、S7 的「±2pp 不劣化」、S8 的「空结果率减半」全都落在噪声量级附近。计划里已经写了「用 dev+test 方向一致代替点估计」的补丁，但那只是降低误判概率，不能消除。

更隐蔽的问题是**dev 半会被过拟合**。S6 允许 8 轮调参、S7 要做阈值 sweep，这两处加起来至少十几次在 dev 上的读数。到 S8 终验时，test 半上的数字大概率会比 dev 低 5–10pp，而那时已经没有预算重做。**如果用户在决策 1 里选了 (b) 90 条，这个风险会显著放大**——这是推荐 (a) 120 条的真实原因。

### 风险 3　S4 的 top-30 截断可能在核心 20 条上悄悄失血，而它的代价在 S6 才显现

C-4 的核心 20 条是零余量契约，掉一条即红。这 20 条里有 `"我是谁"`、`"打印文字"`、`"退出码"`、`"反向解析"` 这类极短查询——2-gram 切出来只有 2–3 个 term，BM25 在这种极短查询上区分度很低，top-30 里塞进一堆噪声规则是完全可能的。S4 因为还用 v1 打分重排，正确答案只要进了 top-30 就还能被顶回 Top-1，所以 S4 可能全绿；但到了 S6 换成余弦打分，短查询的区分度问题会和召回噪声叠加，这时候才暴露，而那时要改的是 S4 的召回层——**跨阶段返工，且要重跑 S5 之后所有阶段的对照**。

计划里的「召回包含性」硬门槛（S4 验证表）是针对这一点设的，但它只检查「正确答案在不在 top-30」，不检查「top-30 里的噪声有多少」。真正的守卫应该是「短查询（≤ 4 字符）的 `recall@30` 与 `precision@30` 分开统计」，这一条我在 S4 的 bench 需求里写了 `recall@30`，但 precision 侧没有设门槛——因为我也不知道该设多少。**这是本计划里我最没有把握的一个数字。**
